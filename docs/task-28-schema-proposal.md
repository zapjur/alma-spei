# Task #28 — minimum donor, payment and audit schema proposal

Status: APPROVED by the user on 2026-11-07. The user approved this exact schema
after reviewing the proposal. [Structural discovery](source-inspection.md) is
available, but does not resolve historical financial semantics. No new dependency
is introduced. The sections below retain the reviewed design wording.

## Proposed scope and tables

Use one new ordered migration after foundation/auth, preserving applied migrations.
Use UUID internal identifiers, foreign keys with ON DELETE RESTRICT, explicit
runtime grants and PostgreSQL timestamps with time zone. Source column positions
are adapter concerns, not donor identifiers.

### `donors`

| Field | Proposed storage / behavior |
| --- | --- |
| `id` | UUID primary key generated by application |
| `entity_type` | Required text, constrained to `individual`, `business`, `organization` |
| `name` | Required nonblank text; full display name, never automatically split |
| `first_name` | Nullable text, explicitly supplied only; preserves card compatibility without inferring a split |
| `street`, `postal_code`, `city`, `province` | Nullable text; preserves incomplete source addresses without inventing values |
| `is_active` | Required boolean default true; routine deletion archives |
| `version` | Required positive bigint default 1; application optimistic concurrency |
| `created_at`, `updated_at` | Required timestamptz |
| `created_by`, `updated_by` | Required references to stable internal `users` |

Manual-create contracts may require a locality under #29, but incomplete imported
source rows remain in staging until validated. Database nullability does not grant
the API permission to bypass its approved validation. PostgreSQL should not impose
a Polish-only postcode regex; the exact UI/import address policy is a later explicit
decision. Do not add gender or taxpayer/spouse fields to donor identity merely
because source headings exist. Do not enforce uniqueness on names or addresses.

Propose B-tree indexes on `lower(name)` and `(is_active, entity_type, id)`; approve
query/search behavior in #30. Do not claim a B-tree accelerates arbitrary substring
search. No fuzzy matching extension or locale change in this task.

### `donations`

| Field | Proposed storage / behavior |
| --- | --- |
| `id` | UUID primary key |
| `donor_id` | Required donor reference with RESTRICT |
| `amount` | Required numeric(20, 4), nonzero; signed facts allow explicitly approved reversals later |
| `currency` | Required three-uppercase-letter code, no default; supported currencies validated by service |
| `received_on` | Required date for established transaction facts only |
| `version` | Required positive bigint default 1 |
| `created_at`, `created_by` | Required timestamp and stable actor reference |

An index on `(donor_id, received_on, id)` supports history reads. No UNIQUE
amount/date/donor key: distinct equal payments can be genuine. Historical yearly
and monthly aggregates must not populate this table as invented transactions.
Import source/batch/row provenance and compensation references are additive #34
work, mandatory before enabling import commit. No arbitrary description text is
stored in the canonical payment table in this first migration.

The numeric precision, permitted negative amounts, currency handling and receipt
date basis are explicit design choices requiring approval, not workbook findings.
Malli/JSON DTOs should represent exact amounts as decimal strings rather than JS
floating point numbers. Imported facts with unresolved required fields stay staged.

### `donor_audit_events` / `donor_audit_changes`

Propose append-only-to-runtime events with UUID, stable actor reference,
`occurred_at`, allowlisted action and donor reference. Changes reference the event
and store an allowlisted field name plus typed JSONB before/after values. Require
one field entry per event/field; represent absence/null explicitly in the service.
Do not place credentials or raw workbook payloads in these tables. No audit edit/
delete runtime grants. Protected read APIs are part of #30, not public access.

Keep domain audit separate from existing authentication security audit. Application
services must write mutation and audit in the same transaction. This schema task
does not pretend grants alone enforce complete audit coverage; #30 tests that path.

## Implementation notes

Implemented in migration `202611070001-donors`. Runtime can read/insert/update
donors, but cannot delete them. Payments are read/insert-only until an approved
correction/compensation service requires narrower additional grants. Audit is
read/insert-only, including no TRUNCATE grant. Audit actions are create, update,
archive and merge; changed fields are the profile fields listed above. JSON null
represents an absent before/after value; SQL NULL is rejected. Nonfinite payment
amount/date values are rejected. No profile API, import, source retention policy
or production deployment is implemented by this migration.
